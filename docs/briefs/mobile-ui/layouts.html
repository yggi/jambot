Jambot on a phone: five layouts

Each frame is a live mock on one shared clock at 108 BPM. All five use the same parts: the transport header with the bar's beats as its background, the same six tab panels and the same play-along footer. Only the arrangement differs. Tap play, stop (twice for a hard stop), loop, the tabs and the play-along chooser.

On a phone the frames stack. On a wide screen they scroll sideways.

Shared by every option

  • The app shell owns the viewport. The body never scrolls. Header, panel, footer and tab bar are grid rows with fixed heights, so nothing that plays can push anything else.
  • One footer height. Keys, pads and chords are all 184 px. Switching between them moves nothing, and opening or closing is one deliberate slide.
  • Nudge before drag. Axes and tempo are −/+ buttons with a gauge between them. A drag needs a horizontal start and never shares a gesture with scrolling.
  • Live riders. A tab's label can carry its card's live main value (key, chord, BPM), so you don't need to open a tab to read it.

Platform, no new dependencies

  • Screen Wake Lock keeps the phone awake while the band plays.
  • CSS scroll-snap gives the swipe pager in B. No gesture library.
  • Container queries fit each panel to the room it has. The app already uses clamp on container units.
  • View Transitions for changing tabs, where the browser has them. Elsewhere the change is a plain swap.
  • PWA manifest: display: standalone, and portrait locked where installed.

Open questions

  • Loop holds the section: is that a wish the composer honours at the section's end (like a key), or a hard repeat of the bars already decided?
  • Should the chords footer show guitar or ukulele shapes, or only names and numerals?
  • Does a client see the transport's play button resting, or does it hide?
  • Where do the extras (tuner, metronome, timing test) live: the lobby, or a seventh tab?

# The analyzer

Facts about `packages/analyzer`.

## The analyzer

- Writing a MIDI file as text is the folder's (MIDI → cells text), so yggi/cells' (D2, cells decision 037; yggi/music-commons#14, ruling 5); the analyzer keeps live hearing (the Muse) and its step grid.
- `packages/analyzer` (#141) is pure, like `theory`, `engine`, `score` and `session`: `loadMidi` runs the analyzer brief's steps 1–3: drop empty and duplicate tracks, split the file into meter spans, quantise every 4/4 span onto the step grid through the engine's own `barAt`/`stepInBar` (T10, never `/16` or `%16` again), and read each track's part role.
  Every other meter is counted and reported, never forced onto the grid or dropped silently.
  `loadMidi`'s own `RawMidi` input, and `parseSmf` (`smf.ts`) that builds one from real Standard MIDI File bytes, both stay in `src/`: `midi-file`, the parser, is itself pure byte-array code (no Node or DOM API), so only reading a file's bytes off disk is a loader outside the package (`experiments/load-file.ts`, milestone 3, run with `node --experimental-strip-types --no-warnings packages/analyzer/experiments/load-file.ts <path>`).
- Swing is found, not assumed: `estimateSwing` (in `packages/engine/src/reading.ts`, one reader with the Muse's, #204) searches its path through the two levels for the value whose `swingMap(swing).written` leaves a 4/4 section's onsets closest to integer steps, and `quantiseSection` reads a section's onsets through the engine's `readOnsets` (swing, then rounding) and keeps what is left, keeping the leftover as each note's microtiming (A6).
  The parser's own tempo map, `ticksTimeMap`, is a `TimeMap` between a file's ticks and seconds built from its own tempo events, the same shape (`played`, `written`, exact inverses) the engine's `tempo.ts` and `swing.ts` already use, but keyed to the file's clock, not a style track's glide, and anchored at tick 0 by whichever tempo event has the smallest tick, never by array order.
- Part roles (`roles.ts`, analyzer brief step 3) read channel 10 as drums, a General MIDI convention independent of #108's still-open seat plan (a file's own channel 10 is drums whatever Jambot's own seats turn out to be).
  Among the rest, a hinted track (its name matching `melody`/`vocal`/`lead`/ `voice`/`sing`, or a General MIDI "Synth Lead" program, 80–87) is lead wherever it sits in the register; otherwise the highest monophonic line is lead and the lowest is bass; everything polyphonic, and any monophonic line between, is harmony evidence.
  Every call carries its own confidence and the rule it used, never a silent guess.
- The parser has its own mini-ratchet, a curriculum (Q10, `packages/analyzer/experiments/ladder.ts`): the engine generates MIDI at rising complexity, and the parser must recover each rung exactly before the next is attempted, before an external corpus (POP909, Groove MIDI, ASAP, Lakh) disturbs the loop with content nothing here wrote.
  Rung 0, `metronomeRung`, reads the engine's own `clicksOf` over the steps of a straight transport and reads its clicks back through `loadMidi`; later rungs (a scale, a real melody, rhythmic patterns, multiple voices, a Bach canon) are #141's continuation.
  A rung generator that needs `@jambot/theory` directly (rung 0's `METERS`) takes it as a devDependency, the same split `packages/score`'s `seam.test.ts` uses for `@jambot/engine`: a lower layer brought in to build or check fixtures, not part of the package's own production code.
- The ladder is also how #63 gets built from the bottom, not only the parser's own measure: `toDrumNotation` (`src/notation.ts`) is the seam between a quantised note and the engine's `WrittenNote`; `toScoreDrums` carries it the rest of the way to `@jambot/score`'s own `DrumLines`, the `encodeBar`/ `compileBar` field E16 decided (L8).
  `toDrumNotation` drops velocity and the microtiming residual (performance, not notation, T4/L7) and writes a role only where the sound alone settles it (kick, pedal hat, the Euclidean rim, every hi-hat sound); `toScoreDrums` reads only `note` and `step`, so it needs no role at all.
  The snare's role (backbeat, fill or ghost) is E16's one remaining open question, so its hits are left out of both rather than guessed.
  Rung 0's hits are all kicks, so it round-trips through real score text end to end (`experiments/ladder.test.ts`): MIDI, through the parser, through `encodeBar`/`compileBar`, and back.
